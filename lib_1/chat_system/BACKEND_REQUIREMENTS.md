# Backend Requirements for Scale

This document outlines the backend endpoints and behaviors required to support the high-scale client architecture.

## 1. Authentication & Connection

### WebSocket Connection
- **URL:** `wss://{host}/ws`
- **Auth:** Token passed as query parameter or in first message
- **Behavior:** Server must maintain persistent connection and broadcast to connected clients

### WebSocket Events (Server → Client)

| Event | Payload | Description |
|-------|---------|-------------|
| `connected` | `{user_id, phone, timestamp}` | Sent on successful connection |
| `new_message` | `{message_id, sender_phone, recipient_phone, content, message_type, sequence_id, client_uuid, peer_user_id, media_url, media_blurhash, timestamp}` | New message from another user |
| `msg_ack` | `{client_uuid, message_id, sequence_id}` | **Critical** - ACK for sent message |
| `message_delivered` | `{message_id, status: 'delivered'}` | Message delivered to recipient device |
| `message_status` | `{message_id, status: 'read\|delivered\|failed'}` | Status update (read receipts) |
| `connection_replaced` | `{reason}` | Another device took over connection |
| `typing` | `{sender_phone}` | Typing indicator |

### WebSocket Events (Client → Server)

| Action | Payload | Description |
|--------|---------|-------------|
| `send_message` | `{recipient_phone, content, message_type, client_uuid}` | Send a message |
| `typing` | `{recipient_phone}` | Typing indicator |
| `mark_read` | `{message_id}` | Mark message as read |

## 2. Message Flow

### Critical: ACK Handshake

When a client sends a message via WebSocket:

```
Client → Server: send_message {client_uuid: "abc-123", ...}
Server → DB: Insert message, assign message_id + sequence_id
Server → Client: msg_ack {client_uuid: "abc-123", message_id: "xyz-789", sequence_id: 42}
Client → SQLite: Update message with server_message_id + sequence_id
```

**Rules:**
- Server MUST reply with `msg_ack` within 5 seconds
- `client_uuid` is generated by client, globally unique (UUID v4)
- `sequence_id` is monotonically increasing per user account
- If ACK is not received, client will retry via outbox queue

### Sequence ID (Monotonic Counter)

- Server maintains a per-user auto-incrementing counter
- Every message (sent or received) gets a unique `sequence_id`
- Used for delta sync to avoid timestamp drift issues
- Never reuse or skip sequence IDs

## 3. HTTP Endpoints

### Send Message (HTTP Fallback)
```
POST /chat/send-message-by-phone/{phone}
Headers: Authorization: Bearer {token}
Body: {
  "content": "Hello",
  "message_type": "text",
  "client_uuid": "abc-123"
}
Response: {
  "message_id": "xyz-789",
  "sequence_id": 42,
  "status": "sent"
}
```

### Delta Sync
```
GET /chat/sync-delta?last_sequence_id=42
Headers: Authorization: Bearer {token}
Response: {
  "messages": [
    {
      "message_id": "xyz-790",
      "sender_phone": "+923001234567",
      "recipient_phone": "+923009876543",
      "content": "Hi there",
      "message_type": "text",
      "sequence_id": 43,
      "client_uuid": "def-456",
      "peer_user_id": "user_123",
      "media_url": "",
      "media_blurhash": "",
      "timestamp": "2026-05-20T10:30:00Z"
    }
  ],
  "last_sequence_id": 43
}
```

**Rules:**
- Return all messages with `sequence_id > last_sequence_id`
- Include both sent and received messages
- Max 500 messages per request
- Client calls this on reconnect and periodically (every 5 min)

### Mark as Read
```
POST /chat/mark-read/{message_id}
Headers: Authorization: Bearer {token}
Response: { "status": "ok" }
```

### Last Seen
```
POST /chat/last-seen
Headers: Authorization: Bearer {token}
Body: { "last_seen": "2026-05-20T10:30:00Z" }
Response: { "status": "ok" }
```

### Delete for Everyone
```
POST /chat/delete-for-everyone/{message_id}
Headers: Authorization: Bearer {token}
Body: { "recipient_phone": "+923001234567" }
Response: { "status": "ok" }
```

**Server Behavior:**
- Notify recipient via WebSocket event `message_deleted`
- Recipient client updates their SQLite

### Edit Message
```
PUT /chat/edit-message/{message_id}
Headers: Authorization: Bearer {token}
Body: {
  "new_content": "Updated text",
  "recipient_phone": "+923001234567"
}
Response: { "status": "ok" }
```

**Server Behavior:**
- Only allow edit within 15 minutes of original send
- Notify recipient via WebSocket event `message_edited`

### Upload Media
```
POST /chat/upload-media-by-phone/{phone}?message_type={type}
Headers: Authorization: Bearer {token}
Content-Type: multipart/form-data
Response: {
  "media_url": "https://cdn.example.com/media/xyz.jpg",
  "status": "uploaded"
}
```

## 4. Phone Number Normalization

Server should normalize phone numbers to a canonical format:
- Strip all non-digit characters except leading `+`
- Convert `03xx` Pakistan format to `+923xx`
- Store as `+923001234567` format in database

Client sends `PhoneNormalization.normalize(phone)` before any API call.

## 5. User ID Mapping

### peer_user_id
- Server assigns each user a unique, immutable ID (UUID or BIGINT)
- This ID is included in all message payloads as `peer_user_id`
- Client stores this in `chats.peer_user_id` and `messages.peer_user_id`
- Used as a stable foreign key, independent of phone number changes

### Phone Number Changes
- If a user changes their phone number, `peer_user_id` stays the same
- Client can merge chat histories by matching `peer_user_id`

## 6. Media Handling

### Upload Flow
1. Client uploads media via HTTP POST
2. Server stores media, returns `media_url`
3. Server sends `new_message` event with `media_url` + `media_blurhash`
4. Recipient sees blurred placeholder immediately
5. Recipient downloads full media in background

### Blurhash
- Server should generate blurhash for uploaded images
- Include `media_blurhash` in `new_message` payload
- Client renders blurhash as placeholder while downloading

### Storage
- Use CDN for media delivery
- Support resumable downloads for large files
- Implement token-based access control (expiring URLs)

## 7. Rate Limiting

| Endpoint | Limit | Window |
|----------|-------|--------|
| Send message | 60/min | Per user |
| Delta sync | 12/hour | Per user |
| Upload media | 20/min | Per user |
| WebSocket connect | 5/min | Per IP |

## 8. Error Handling

### Standard Error Response
```json
{
  "error": "error_code",
  "message": "Human readable message",
  "details": {}
}
```

### Common Error Codes
| Code | Description | Client Action |
|------|-------------|---------------|
| `invalid_token` | Auth token expired/invalid | Force re-login |
| `user_not_found` | Recipient doesn't exist | Show error |
| `message_too_large` | Content exceeds limit | Truncate/reject |
| `rate_limited` | Too many requests | Backoff + retry |
| `media_expired` | Pre-signed URL expired | Re-upload |

## 9. Database Schema (Server-Side)

### Messages Table
```sql
CREATE TABLE messages (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  message_id VARCHAR(36) UNIQUE NOT NULL,  -- UUID
  sender_user_id BIGINT NOT NULL,
  recipient_user_id BIGINT NOT NULL,
  sender_phone VARCHAR(20) NOT NULL,
  recipient_phone VARCHAR(20) NOT NULL,
  content TEXT,
  message_type VARCHAR(20) NOT NULL DEFAULT 'text',
  media_url TEXT,
  media_blurhash VARCHAR(64),
  sequence_id BIGINT NOT NULL,  -- Monotonic per user
  client_uuid VARCHAR(36),  -- Client-generated UUID
  status VARCHAR(20) NOT NULL DEFAULT 'sent',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_sequence (sender_user_id, sequence_id),
  INDEX idx_client_uuid (client_uuid),
  INDEX idx_message_id (message_id)
);
```

### Users Table
```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id VARCHAR(36) UNIQUE NOT NULL,  -- Immutable UUID
  phone VARCHAR(20) UNIQUE NOT NULL,
  normalized_phone VARCHAR(20) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

## 10. Scaling Considerations

### Horizontal Scaling
- Use Redis for WebSocket session management
- Use message queue (RabbitMQ/Kafka) for message routing
- Implement connection affinity (sticky sessions) or pub/sub for WebSocket

### Message Ordering
- Sequence IDs guarantee ordering per user
- Use database transactions when assigning sequence IDs
- Never assign sequence IDs out of order

### Offline Support
- Server should buffer messages for offline users (up to 7 days)
- Delta sync retrieves all missed messages on reconnect
- Use sequence_id gap detection to identify missing messages
